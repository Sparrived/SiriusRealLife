# 架构

## 1. 项目是什么

SiriusRealLife 是一个**人格模拟器**。人格是一个**有限状态机 + 意识流**：

- 任一时刻只持有**一个**状态
- 状态由 **LLM 决定**：框架给出事实与硬约束，模型自己选换不换、换去哪、待多久
- 状态 = 一段有明确出口的过程：目标 + 信息可见性（订阅哪些频道）+ 退出条件
- 时间由固定 **tick** 驱动。**框架里没有随机**——想要"不作为"就显式选择等待

技术栈：**Go** 后端 + **Vue 3** 前端。LLM 全部经 AMKR（见 [`llm-amkr.md`](llm-amkr.md)）。

目标不是"一个会聊天的 LLM"，而是**一个能自己待着、自己决定下一秒干什么的存在**。行为要像个有作息的人，而不是一个等输入的问答接口。

---

## 2. 核心模型

五个概念，互相正交。**不要把它们合并**（合并会直接导致状态爆炸，见硬规则 R2）。

### 2.1 状态（state）

离散枚举，有明确出口条件。一个状态声明的是**框架对 LLM 的全部约束**：

| 字段 | 说明 |
|---|---|
| `guard` | 前置条件，不满足则**不进候选清单**（模型看不到它） |
| `minTick` / `maxTick` | 停留时长的**硬边界**，模型给的 `for_ticks` 被夹进这个区间 |
| `cooldown` | 冷却期，刚离开的状态短期内不进候选 |
| `until` | 状态自己的退场条件（"该结束的迹象出现了"），作为**理由**注入 prompt |
| `channels` | 该状态下**订阅哪些频道**（如仅"看 QQ"状态持续收到 QQ 消息） |
| `suggests` | **建议动作**（进 prompt 提示"现在适合做什么"），非硬白名单 |
| `energyPerTick` | 逐 tick 的精力开销（负值为回复），使"待了多久"决定花费 |
| `onEnter` / `onExit` | 进入/退出时的副作用（只允许改心境与写意识流） |

状态**没有权重**。没有"按概率被抽中"这回事——`Weight`/`WeightMod`/`Blocks`/`Visibility`/`Uninterruptible` 都已删除。

状态**不携带情绪**。`ANGRY_WORKING` 是错的（R2）。

#### 状态是一段订阅，不是一次跳跃

状态决定的是"**这段时间里她在做什么、看得见什么**"。进入 `scrolling_phone` 并不是"跳到手机前看一眼再跳回来"，而是**接下来若干 tick 都待在手机前**——期间 QQ 消息每 tick 泵入、即时呈现给她。

这正是"如何持续一个状态"的答案：**不靠循环，靠订阅**。框架每 tick 把该状态订阅的频道泵进去，直到她决定离开。

三种退场入口汇合到同一个决策点（见 R11、§2.3）：
1. **检查点**到点 —— `for_ticks`，也就是模型上次说的"下次什么时候问我"
2. **`until` 成立** —— 状态自己判断"该结束了"（如睡饱了、刷够了、安静太久了）
3. **`maxTick` 兜底** —— 硬上限，防止一次失败的降级让人格永远赖着

三者都只往 `pending` 里追加一条理由，最后由**一次**决策把全部理由摆在模型面前，由它选 `stay` 还是 `enter_state`。

**入口分两类，这是踩过坑的地方。** 检查点是**事件**——到点就消失（`decideAt` 被推进到下一次），天然只报一次。
`until` 与 `maxTick` 是**条件**——一旦成立就**持续**成立（"精力 < 30"不会自己变回去，"已经超过上限"更不会）。
若按"条件成立就问"，决策点会连轴转：模型填的 `for_ticks` 形同虚设，每个 tick 都变成一次真金白银的 LLM 调用。

因此条件型入口按**上升沿**报：由假变真时报一次，之后闭麦，直到条件重新变假再变真。两个 bool 标记
（`untilReported` / `maxReported`）在进入新状态时清零。

> 线上实测过这个缺陷：85 次决策的相邻间隔**中位数是 3**，而模型填的 `for_ticks` 是 12。
> 症状很隐蔽——人格看起来"在正常工作"，只是被反复打断、很难连贯做完一件事，而账单在悄悄涨。
> 回归测试见 `TestConditionTriggersFireOnce`、`TestDecisionCadenceRespectsForTicks`
> （两者都做过变异验证：把上升沿改掉，它们立刻失败）。

#### `until` 能表达什么：以"退出订阅"为例

`until` 是一个 `func(*Agent) bool`，因此它能读到 agent 的全部可观测事实。这一点很重要——**没有访问器，条件就写不出来**。

用户提过的场景："长时间没收到消息，可以作为退出订阅的条件"。它需要先能回答"安静多久了"，因此有了 `Agent.QuietFor() (Tick, bool)`：

```go
// 刷手机：刷太久，或安静太久，就该干点别的了。
func quietEnoughToLeave(a *Agent) bool {
	if a.Now-a.enteredAt >= 8 {
		return true
	}
	quiet, _ := a.QuietFor()
	return quiet >= 20
}
```

第二个返回值区分"**安静很久**"与"**从来没人说过话**"——前者是"没人理我"，后者是"世界还没开始"，含义完全不同，不能拿一个大数字糊过去。

`until` **只说"该结束了"，不说为什么**（它只是个 bool）。因此框架在渲染理由时补上它确实知道的**外部可观测事实**（"已经 8 tick 了""最近 20 tick 都没有新消息"），让模型能判断该不该当真。**仍然只是提供理由，不替它做决定**（R11）——安静 20 tick 后她可以照旧赖着。

### 2.2 心境（mood）

连续量，随时间自己衰减，例如精力 / 烦躁 / 好奇 / 亲密度。心境不参与状态枚举，只做两件事：

- 影响状态自己的 `guard` / `until`（累了才进得去睡觉、也才该醒）
- 影响 prompt 文字与工具参数

影响方向是**单向**的：心境 → `guard`/`until`/prompt/参数；状态 → 只能改心境和意识流。

心境只提供**事实与建议**，不替模型做决定：框架写"我累了"，不写"所以你该去睡觉"。要不要歇、什么时候歇，是模型看到这条事实后自己选。

衰减速率是**人格参数**（`fsm.MoodRates`），不是散在代码里的字面量：它直接决定人格"像不像人"，要能按人格调、能被测试断言。

#### 精力必须收支平衡（易错点）

精力唯一的回复手段是睡觉（`sleeping.EnergyPerTick = -0.5`，逐 tick 回复）。因此**净回复必须为正，且能在 `maxTick` 之内从 `guard` 的下限睡到 `until` 的上限**，否则精力会长期钉在 0，人格失去"累"的层次——而所有单元测试照样通过，只有跑一整天数据才看得出来。

同理，状态的精力成本必须与**停留时长**成正比：`working` 一天进入几十次，固定扣费等于按"次数"收钱，与"实际干了多久"无关。现在是逐 tick 计费（`working.EnergyPerTick = 0.02`），对"实际待了多久"天然正确。

这个平衡由两条测试守住，调 `DefaultMoodRates()` 或状态成本后必须重跑：

- `TestSleepRecoversFasterThanDecay` —— 直接算算术前提（净回复 > 0，且 35→90 落在 `[minTick, maxTick]` 内），不靠跑
- `TestMoodEconomyBalanced` —— 跑 7 个游戏日，断言精力为 0 的占比与最长连续时间

### 2.3 决策点（decision point）

在"该问它了"这一刻被调用。流程：

1. `due()` 收集本 tick 成立的理由（检查点 / `until` / `maxTick`），追加进 `pending`。
   注意**判断依据是 `pending` 非空**，不是"本 tick 有没有新理由"——条件型入口只在上升沿产出理由，
   若上一次要问时恰好有独白在途，理由会被攒下来而 `due()` 不再产出，按后者判断就会把它永久搁置
2. 已有在途调用就把理由**留着**，下个 tick 再问（一次只允许一个调用在途）
3. `survey()` 盘点所有状态此刻的可选性，形成完整清单——**这是框架约束的唯一入口**：
   - 当前状态 → 挡掉（想继续要用 `stay`，那是另一件事，有自己的理由与时长）
   - `guard` 不满足 → 挡掉
   - 冷却中 → 挡掉
4. 候选状态名进 `enter_state` 的 JSON Schema `enum`，被挡的连同原因写进描述
5. 模型调 `stay(why, for_ticks)` 或 `enter_state(state, for_ticks, why)`
6. `applyDecision` 处理：**只有第一个被识别的调用生效**

**约束落在协议层，不落在散文里。** 模型在 schema 层面就无法选到一个此刻不能进的状态，这比在 prompt 里写"请不要选睡觉"可靠得多。但校验仍要兜底（`commitEnter` 会再查一次 `inMenu`）：**支持与否逐路由不同**，无视 `tools` 的路由会让模型只回散文，那时必须挡住而不是照做。

**失败一律降级为 `stay`，绝不用随机兜底。** 没调工具、调了不认识的名字、选了不可进的状态、LLM 调用失败——全都降级成"原样再待一会然后重问"，理由是框架给的。降级的存在理由只有一个：没有它，一次失败就意味着永远不再问，人格会卡死在一个状态里。

**可复现性不靠种子。** 框架里没有随机数，因此没有 `Seed`、没有 `*rand.Rand`。复现靠**决策日志**：同一个模型（或同一个假 LLM）给同样的输入必然给出同样的决定，且每步都能在日志里查到当时的选择、理由与完整候选清单。这也是排障时唯一能回答"她为什么从没去过睡觉"的东西。

### 2.4 tick

真实时间与游戏时间的换算**只在 tick 源头做一次**（R8）。业务逻辑只认 tick 序号，不认 `time.Now()`。

每个 tick 的顺序是固定的（`Agent.Step`）：

1. `drainEvents` —— 处理外部事件与 LLM 结果（R1：只在自己的 goroutine 里改状态）
2. `Now++` → `decayMood` → `chargeState` —— 时间前进，心境衰减，按当前状态逐 tick 计费
3. `ticker.Tick` —— 驱动记忆层衰减/升格
4. `Pump` —— 把当前状态**订阅**的频道泵进意识流。**在决策之前**，这样本 tick 到达的消息能参与这次判断
5. `consider` —— 决策点到点了就问一次 LLM（异步发起，不阻塞本 tick）
6. `emit` —— 推送快照给观察者

这样离线推演、加速、回放全部免费拿到 —— 也是唯一能让"跑 30 个 tick 验收"变成确定性测试的办法。

### 2.5 意识流（memory）

分层存储，各自有界（R5）。**层结构、打捞、遗忘、自我模型的完整定义见 [`memory.md`](memory.md)——该文档是唯一来源。**

速览：

| 层 | 用途 | 进 prompt |
|---|---|---|
| `working` | 当前状态的即时上下文 | ✅ 是 |
| `staging` | 待选区，关键词打捞、记忆曲线 | 打捞后部分进 |
| `event` | 事件记忆，向量 + 关键词两路召回 | 打捞后部分进 |
| `consolidated` | 整合记忆，细节已丢 | 可被检索 |
| `self-model` | 自指陈述，有界 | ✅ 常驻 |
| Shadow | 存档但 LLM 不可读 | ❌ 永不 |

**prompt 只读 `working` + `self-model` + 打捞结果。** 任何往 prompt 里塞全量历史的代码都是 bug。

`working` 的载体是**带类型的意识流**（观察/想法/动作/打算），它是一份 append-only 日志；送进 LLM 的是从这份日志按调用点装配出的**视图**，组装规则见 [`memory.md`](memory.md) §8。日志与视图必须分开：日志要全、视图要有界。

**消息到达不触发决策**（R12）。外部消息只有两件事可做：喂给订阅了该频道的状态（`Pump`），以及更新计数与条件状态（未读数 → 烦躁）。控制流里不准出现"因为来了一条消息，所以去决定/换状态"。`@` 与回复不是抢占信号，只是"这条未读更显眼"。

### 2.6 数据流

```
真实时间 ──► tick 源（唯一做时间换算的地方）
                │
                ▼
        ┌───────────────────────┐
        │  agent goroutine      │  ◄── 事件 channel（唯一入口）
        │  select { tick / 事件 }│
        └───────────┬───────────┘
                    │ 本 tick 有理由吗？（pending）
                    ▼
              决策点：survey() 出候选清单 ──► 工具 schema（enum 即约束）
                    │
                    ▼
        LLM 调 stay / enter_state / read_app（异步，可取消）
                    │
                    ├─ read_app：读内容 ──► 用刚读到的内容打捞记忆
                    │              ──► 工具结果轮（SiteToolRead）
                    │                  只带 send_message，**不改状态**
                    │              ──► 重新问一次决策（次数有预算）
                    ▼
         applyDecision ──► enter() ──► OnEnter ──► 订阅下一段
                    │
                    ▼
        写 working memory ──► 结构化决策日志（R6）──► SSE ──► Vue
```

**并发模型**：一个 agent 一个 goroutine，状态只被它自己改（R1）。其他 goroutine 想影响 agent 只能投递事件，不准持锁直接改状态。

## 3. 目录结构

```
cmd/sirius/          程序入口，只做装配（读配置、建 agent、起 http、起 tick 源），不放业务逻辑
internal/fsm/        状态机核心：状态定义、决策点、tick 循环、心境、意识流、上下文装配、Attention/Ticker/Sink 缝口
                     state.go 状态声明 / states.go 状态表 / decide.go 决策点与工具
                     dispatcher.go 候选清单 / think.go 异步调用 / agent.go tick 与事件
internal/llm/        LLM 客户端。唯一实现是 AMKR 的 OpenAI 兼容接口（含 tool calling）
internal/memory/     记忆分层：staging / event / consolidated / self-model / Shadow
internal/transport/  HTTP 路由 + SSE 推送 + AMKR WebUI 反代
internal/config/     环境变量配置与校验（含回环地址硬校验）
internal/tick/       唯一的时间换算点（R8）：真实时间 → tick
internal/acceptance/ roadmap §2 验收标准的端到端测试
config/              状态表、prompt 模板（尚未落地，见下）
web/                 Vue 3 + Vite + TS 前端
docs/                本目录
```

心境**不是**独立包：它与状态机强耦合（`guard`/`until`/衰减/prompt），拆开会造成
`fsm` ←→ `mood` 双向依赖，因此与状态定义一起放在 `internal/fsm`。

新目录必须有明确归属，不进 `internal/` 就别建。禁止 `utils/`、`common/`、`helpers/`、`models/` 这类无主题垃圾桶。
