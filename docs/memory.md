# 记忆与注意力模型

本文档定义 Sirius 的**注意力门控、记忆分层、打捞、遗忘、自我模型**。是 AGENTS.md R5 的实施细则，也是**记忆分层定义的唯一来源**。

设计由项目作者提出，本文档负责整理、补齐机制、给出可实现的初值。

---

## 1. 设计目标

模拟一个**有注意力的存在**，而不是随时待命的问答接口。

核心命题：**信息可见性不是全开的。** 没在"看 QQ"时，群消息不该进入模型视野——就像真人不会盯着屏幕等消息。

---

## 2. 注意力门控

### 2.1 三类消息

消息**不改变状态**。`@` 不是抢占信号（R12）——真人不会因为手机响一声就放下手里的事。三种消息的区别只在**这条未读有多显眼**：

| 类型 | 行为 | 现实对应 |
|---|---|---|
| `@我` | 静默入队，**标记为"提到我了"** | 消息列表里那一条带红字提醒 |
| **回复我**（引用/回复我的消息） | 同上 | 同上 |
| 其他 | 静默入队，未读计数 +1 | 群消息静默，只有红点数字 |

三者的共同点：**都只入 unread 队列、都推高烦躁**，都不掐断她手上的事。区别在于**"更显眼"落在两处**：

| 处境 | 落点 | 表现 |
|---|---|---|
| 还没看手机 | `UnreadMentions()` → prompt 的【手机】段 | "还有 5 条没看，**其中 1 条提到了你**" |
| 正在看手机 | `formatMessage` 渲染正文 | "**（提到了你）**张三: 在吗" |

> ⚠️ 这两处**缺一不可**，而且很容易只做一半：抢占取消后，@ 与普通消息的差别
> 若只落在入队的 `Importance`（淘汰优先级）上，模型**永远看不到**它——
> 那 @ 与灌水在人格眼里就完全等价了。曾经 `formatMessage` 只拼
> `发送者: 正文`，【手机】段也只报条数，于是文档里"前两类在 prompt 里被
> 显式标出来"是句空话。回归测试：`TestMentionAndReplyAreMarkedInContent`、
> `TestContextReportsUnreadMentions`。

**那她什么时候才会去看？** 下一次决策点（检查点到点 / `until` 成立 / `maxTick` 兜底）把"有 N 条未读""有人提到我"作为**理由**摆给模型，由它决定要不要换到 `scrolling_phone`。这也是"手机响了但她在忙，过一会才想起来看"的自然表达。

**睡眠期间同样如此。** `sleeping` 刻意**不订阅** QQ（`channels` 为空），因此睡着时消息既不进 prompt 也不打断——它们只在 unread 队列里累积，等她醒来后由烦躁与未读数把它推向"去看看"。这比旧的 `uninterruptible: true` 更准确：**被门控的是信息，不是抢占规则。**

### 2.2 unread 队列

- **有上限**（R5）。超出时按重要性丢弃，不是丢最旧的
- 保留**未读计数**，它是心境输入（99+ 推高"烦躁"）——这是**唯一**的累积通道。抢占取消后，没有它，消息再多人格也毫无反应
- 内容只在**订阅了 QQ 的状态**里被读取；`Pump` 每 tick 泵一次，因此驻留期间新到的消息会持续呈现（"状态是一段订阅"）

### 2.3 读取两级

1. **进入状态**：显式返回最近 N 条（模拟"解锁手机扫一眼"）
2. **翻阅工具**：主动向前翻页

**必须有已读游标（read cursor）**，否则"最近几条"永远返回同样内容，状态退出再进入会空转。

## 3. 记忆分层

```
消息
 │ 静默入队（**不打断**，@ 只是更显眼）
 ▼
unread 队列 ──进入"看QQ"──► 最近N条直接进 working
 │
 │ **看手机时看到的都写入**（Scan/Browse 的副作用，自动）
 │ 同一次翻阅按时间邻近合并为一段
 ▼
┌──────────────────────────────────────────────┐
│ 1. 记忆待选区 staging                          │
│    · 只用【关键词打捞】                         │
│    · 打捞返回「某次翻阅的全部上下文」（整段）     │
│    · 记忆曲线衰减，长期不打捞 → Shadow          │
└──────────────────────────────────────────────┘
 │ 升格条件达成 → 源条目【删除】
 ▼
┌──────────────────────────────────────────────┐
│ 2. 事件记忆 event                              │
│    · 向量召回 + 关键词赋分两路融合                 │
│    · 长期低频 → LLM 整合，源条目 → Shadow        │
└──────────────────────────────────────────────┘
 │ LLM 整合
 ▼
┌──────────────────────────────────────────────┐
│ 3. 整合记忆 consolidated                       │
│    · 抽象摘要，细节已丢                         │
│    · 两个出口：可被检索 / 自指部分 → 自我模型     │
└──────────────────────────────────────────────┘
 │ 自指内容
 ▼
┌──────────────────────────────────────────────┐
│ 4. 自我模型 self-model                         │
│    · 有界陈述列表，【常驻 prompt】               │
│    · 由经历学习而来，可被新证据修正               │
└──────────────────────────────────────────────┘

横切：working memory —— 当前状态的即时上下文，进 prompt 的就是它（详见 §8）
终态：Shadow —— 存档但 LLM 不可读
```

### 3.1 Shadow 的确定语义

**Shadow = 存档但不再被 LLM 读取。**

- 数据保留在存储中，**可审计、可回放**（回答"agent 忘了什么"）
- **不参与任何打捞排序**，不再刷新记忆曲线
- 任何层都能进 Shadow，它是终态

⚠️ 与"物理删除"的区别：Shadow 仍可被**人**查询（调试/审计接口），但**绝不**进入 prompt。

### 3.2 一条统一不变式

> **每次"抽象化"（升格、整合）都消费源条目。**

| 转换 | 源条目去向 | 理由 |
|---|---|---|
| staging → event（升格） | **删除** | 保留会导致同一条被反复升格，生成多个相似事件记忆 |
| event → consolidated（整合） | **进 Shadow** | 对应"记不得细节"：细节不再可读，但存档可审计 |

两者处理不同是**有意的**：升格是"换个粒度重存"（内容等价，留着是冗余）；整合是"细节丢失"（内容不等价，留着是证据）。

## 4. 遗忘：三层机制

| 机制 | 触发 | 结果 | 成本 |
|---|---|---|---|
| **记忆曲线衰减** | 长期未被打捞 | 沉入 Shadow | 零（只改权重） |
| **LLM 整合** | 事件记忆长期低频 | 细节丢失，只留摘要 | 一次 LLM 调用 |
| **重要性淘汰** | unread 队列满 | 直接丢弃 | 零 |

**记忆曲线按 tick 衰减，不按 wall clock**（R8）——否则回放会失真。

曲线模型：每条待选区条目持有强度 `S ∈ [0,1]`，初始 1.0，每 tick 衰减；被打捞则**刷新为 1.0**。`S < 0.1` 时进 Shadow。

> 与论文一致：其 recency 是"自**上次被检索**以来的小时数"的指数衰减（系数 0.995），即**检索行为本身刷新 recency**。"被反复想起的事更持久"与"高频打捞→升格"是同一结构。

## 5. 打捞

### 5.1 待选区：关键词打捞

- **看手机时看到的都写入待选区**（自动，不经工具调用）
- 关键词在写入时由**本地词元化**产出（中文 2/3-gram + 拉丁整词），不只存原文
- 打捞把查询也切词元后按重合度匹配，**返回整段翻阅上下文**

**为什么写入是自动的：** 写入挂在"看到"这个动作上，而不是挂在一次工具调用上。`read_app` 只负责**看到内容**（它没有关键词参数），回复走另一个工具。看到即入记忆，此后才谈得上打捞、升格、遗忘。

**为什么关键词是本地切的：** 写入既然是自动的，就不能依赖额外一次 LLM 调用（§5.1 原写"存储时由 LLM 生成关键词"，那需要一个调用点）。本地词元化零成本、零依赖。
> `ponytail:` 本地 2/3-gram 的召回不如 LLM 生成的关键词准（同义词、代词仍匹配不上）。升级路径就是下面的查询扩展：让独白顺带产出关键词即可（独白本来就在回看刚发生的事），不必新增调用点。

**为什么返回整段：** 单条消息脱离上下文会失去含义（"那你去吧"指什么？）。以"一次翻阅"为检索单位，等价于人类的情节记忆——想起的是"那天翻到的那一段"，不是孤立一句话。会话按**时间邻近**合并（间隔 ≤ 30 tick 算同一次翻阅），否则 Pump 每 tick 捞到一条就开一段，每段只剩一句话，恰好退化成它想避免的孤立单条。

**匹配规则：** 两侧都切词元后数重合，且按**稀有度**加权——只在这一条里出现过的词元一个就够，常见词需要两个以上互相印证。
> 为什么要加权而不是固定阈值：打捞有**副作用**（刷新强度、累计升格次数），"什么都捞"会把无关内容一路顶成事件记忆；而固定要求两个词元又会漏掉最该命中的情况——短条目（"周末去看展吗"）与整句查询通常只共享一个词。

**已知弱点：** 同义词、代词、隐含指代匹配不上。**补偿手段：查询扩展**——打捞前让 LLM 先产出若干关键词/近义表达再逐个匹配。比引 embedding 便宜得多，且不依赖外部服务。

### 5.2 事件记忆：向量召回 + 关键词赋分

**向量库是 Sirius 的自有资产，不是可省项。** 必须分清两件事：

| 关注点 | 归属 | 说明 |
|---|---|---|
| embedding **计算** | AMKR | 一次 HTTP 调用，外部依赖，可换 |
| 向量**存储与检索** | **Sirius** | 索引、持久化、余弦检索、与关键词融合排序 |
| 融合排序策略 | **Sirius** | 两个分怎么加权，是人格行为的一部分 |

AMKR 的**下一个版本**起把 embeddings 作为一等 route mode 原生支持（`unified_model.embeddings`、上游 `v1/embeddings`）；`v4.1.0` 及更早没有。它是普通 OpenAI 兼容端点，Sirius 侧**无需适配**——但这只省掉"自己跑模型"的成本，**不减少向量库本身的实现工作**。

**实现约定：**

- **纯 Go 标准库，不引外部向量库**（符合反目标）。1 个 agent、记忆条目有界，**暴力余弦**足够，不需要 HNSW/ANN。
- 向量**与记忆条目存在一起**（同一条记录带 `[]float32`），不搞独立索引服务。
- **换 embedding 模型必须重建索引**：维度与语义空间都会变。参考 ai-town 的教训（[`prior-art.md`](prior-art.md) §4）——维度不匹配会导致静默错误。因此**记录里存 embedding 模型标识**，与当前配置不符的条目视为待重算。
- **向量必须落盘**：它是项目资产，且重启后重算 embedding 等于重复付费调 AMKR（这是"v1 全内存"的唯一例外）。
- 检索是**两路融合**：向量余弦（relevance）+ 关键词（精确命中，防止专有名词被语义漂移掉），二者归一化后加权。

**分期：** 向量库在 **Phase 2** 随整合一起落地（那时才真正需要跨语义检索）。Phase 1 先用关键词验证"遗忘与打捞"机制本身——这只是**顺序**，不是"可能不做"。

### 5.3 升格与整合的触发条件

| 转换 | 条件（初值，可调） |
|---|---|
| staging → event | 滑动窗口（最近 **100 tick**）内被打捞 **≥ 3 次**；**或** `importance ≥ 7` 且被打捞 ≥ 1 次 |
| event → consolidated | 距上次打捞 **> 2000 tick** 且累计打捞 ≤ 2 次（即"长期低频"） |

⚠️ **必须同时使用 importance 做对冲。** 只用频率会形成**富者愈富**：被打捞→刷新曲线→更易再被打捞。"被 @ 的那条重要消息"会因没人翻到而消失。
**代价几乎为零**：让 LLM 在写入待选区时**顺手打 1–10 分**（与生成关键词合并进同一次调用）。

## 6. 自我模型：整合记忆如何影响行为

这是"整合记忆不该只是墓碑"的答案。

### 6.1 两条通道

整合记忆通过**两条独立通道**影响行为：

| 通道 | 机制 | 效果 |
|---|---|---|
| **A. 检索** | 整合记忆参与事件记忆**同一套打分**，可被主动打捞 | 显式回忆："我们以前常聊" |
| **B. 常驻** | **自指**内容经提炼进自我模型，**始终在 prompt 里** | 隐性倾向：不必"想起"就已塑造行为 |

**通道 B 是关键。** 人不会"回忆"自己是内向的人——这塑造了行为却从不被主动想起。只有通道 A，整合记忆就只是可检索的摘要，浪费了"细节已丢失、只余倾向"这一特性。

### 6.2 自我模型的形态

| 属性 | 规定 |
|---|---|
| 内容 | **自指陈述**列表："我是个爱钻研的人"、"我和 X 关系不错" |
| 上限 | **20 条**（有界，R5） |
| 每条字段 | 陈述文本、支撑计数、最近支撑 tick |
| 更新时机 | 新整合记忆产生时，LLM 做一次增量更新：新增 / 加强 / 削弱 / 删除 |
| 衰减 | 长期无新证据支撑 → 强度下降 → 也可进 Shadow |
| 初始种子 | **人格设定文件中作者写入的初始特质** |

> **自我模型是人格设定的"学习态"。** 人格设定是作者写死的初始值；自我模型是它经历之后的样子。二者结构相同，前者是后者的初始种子。

### 6.3 与心境、状态的关系

三者正交，不可合并（R2）：

| | 时间尺度 | 影响 |
|---|---|---|
| **状态** | 分到小时 | 当前在做什么 |
| **心境** | 小时到天 | 状态的 `guard`/`until`、prompt 语气 |
| **自我模型** | 天到永久 | prompt 中的自我认知 |

心境是**短期**波动（今天累了），自我模型是**长期**认同（我本来就不爱social）。二者都会影响 prompt，但含义不同——不要把它们合并成"情绪值"。

## 7. 与硬规则的关系

| 规则 | 对应 |
|---|---|
| **R5**（意识流有界） | 各层边界见 §3；unread 上限见 §2.2；自我模型上限 20 条见 §6.2 |
| **R12**（消息不触发决策） | 三类消息只入队、只改计数（§2.1）；换不换状态留给下一次决策点 |
| **R2**（状态/心境正交） | 自我模型是**第三个**独立的慢变量（§6.3）；心境不参与记忆存储 |
| **R8**（只认 tick） | 记忆曲线、升格窗口、整合触发全部按 tick 计 |

### 7.1 R7 的修订（已生效）

AGENTS.md R7 原写"状态声明工具**白名单**"，现修订为：

> 状态声明的是**信息可见性**与**建议动作**，不是工具白名单；只在有明确安全/一致性理由时才硬封锁具体工具。

**依据**（`prior-art.md` §3.3）：把工具可见性绑死到状态会导致状态一多就组合爆炸，并挡住模型在意外情境下使用正确工具。

**你的 QQ 设计正是这个例外的正当理由**：被门控的不是工具，而是**信息**——不在"看 QQ"时，`read_app` 之类工具**仍可用**，只是没有 QQ 消息显现。

## 8. working 层与上下文装配

`working` 是"进 prompt 的就是它"的那一层（§3 图末）。它不是一个额外的存储，而是**从意识流 + 长期层里按用途取出的视图**。

### 8.1 意识流是带类型的日志，不是一个 prompt

意识流是唯一贯穿所有人格活动的数据结构，但它**不是**一份拼好的 prompt。两者的区别是本节的全部要点：

| | 意识流（日志） | 上下文（视图） |
|---|---|---|
| 性质 | append-only、有界、**全类型** | 每次调用现算、**按需取子集** |
| 谁读 | 前端、调试、本节的装配器 | LLM |
| 边界 | 固定 100 条（R5） | 每段各自有上限（R5） |

**为什么必须分开：** 三个调用点要的东西不同。

| 调用点 | 要什么 | 不要什么 |
|---|---|---|
| `dispatch`（状态分派） | 我在哪、心境、能做什么 | 三小时前的琐事 |
| `monologue`（内心独白） | 最近在想什么、刚发生了什么、打算做什么 | 全量历史 |
| `tool_read`（工具解读） | 工具返回了什么 | 人格背景 |

共享的是**上下文装配**，各自追加的追问在调用点。把它们塞成一个大 prompt 只会烧 token 并让模型失焦（R5 的反面）。

### 8.2 记录类型

每条意识流记录带一个类型。类型让"最近在想什么 / 做了什么 / 接下来准备做什么"在**数据结构上**可区分——否则装配器只能把它们混成一段流水账。

| 类型 | 含义 | 谁写 |
|---|---|---|
| `observation` | 看到/收到的东西：消息、工具返回、环境变化 | `ReadPhone`（受 QQ 门控）、消息入队提示 |
| `thought` | 内心独白 | 独白的 `thought` 字段、前缀解析、整段兜底 |
| `action` | 做了什么 | 状态表的 `OnEnter`、独白的 `action` 字段 |
| `intent` | 接下来打算做什么 | 独白的 `intent` 字段 |

> 分层依据 CoALA（arXiv:2309.02427 §4.1）：working memory 存"当前情境 + 近期感知 + 目标 + 中间推理"，episodic 存"过去行为的序列"。我们用一条带类型的**日志**承载两者，由装配器按用途切分。
>
> 这与 Generative Agents 的做法一致：它不维护"一段记忆文本"，而是维护带 `type`/`importance` 的结构化记录，再用检索函数挑子集。

### 8.3 意图跨状态存活

"接下来准备做什么"**不是一个字段，而是日志里最新的一条 `intent`**。

理由：字段会被状态切换清掉，而"我原本打算做什么"恰恰要跨状态活着。若不存在，agent 每次换状态都像换了个人——这是修复前最明显的失真。

装配时取**最新一条** `intent`，因此"打算"会一直显示到被新的打算覆盖。它不设过期：真人也不会因为刷了会儿手机就忘了要干活。

### 8.4 装配出的段落

每段都可省略（内容为空即不出现），每段都有上限：

| 段落 | 来源 | 上限（初值） |
|---|---|---|
| 【现在】 | 时刻、状态、心境 | 固定 |
| 【我是谁】 | 自我模型（§6.2，通道 B） | ≤20 条 |
| 【最近在想】 | 最近 N 条 `thought` | 5 |
| 【刚发生】 | 最近 N 条 `observation` + `action` | 8 |
| 【打算】 | 最新一条 `intent` | 1 |
| 【想起的事】 | 关键词打捞结果（§5.1） | 5 |
| 【适合做】 | 当前状态的 `Suggests`（R7 修订） | 状态自带 |

**观察与动作合并进同一段**：对"我刚做了什么、发生了什么"这个问题，看到消息和起身去倒水是同一串因果，拆开反而读不出顺序。

**打捞查询词用意图 + 最近的想法**，不用状态名——"刷手机"这种词捞不出有意义的往事；用"此刻在想什么"去捞旧记忆才是联想。

### 8.5 独白的触发与成本

独白在**进入状态时**发起（`OnEnter` 之后，这样上下文里已包含"我刚进入这个状态"）。它满足 R4：异步起 goroutine，结果以事件回到 agent，期间照常收事件、照常泵入订阅的消息。

触发点必须是**进入状态**，不能挪到 tick 循环里逐 tick 调用：后者在节流关掉时（`SIRIUS_MONOLOGUE_EVERY=0`）会变成每 tick 一次 LLM 调用——既贵，又会让在途通道永远占满，决策再也插不进去（一次只允许一个调用在途，决策优先）。

**必须有节流。** 状态平均只停留几 tick，不节流会变成每次转移一次调用。间隔由 `SIRIUS_MONOLOGUE_EVERY` 控制，默认 30 tick（游戏内半小时）——够让上下文真的变化，又把量压到一天几十次。

**被取消的调用不记为失败。** 关停会取消在途独白；那不是故障，不该在意识流里写"没想出来"，否则关停看起来像出错。

**结构化输出请求一次，但不依赖它。** 独白是一次"要三个字段"的调用：`thought` / `action` / `intent`。做法分两层，缺一不可：

1. **请求**：`ChatRequest.Schema` 非空时，客户端发 OpenAI 的 `response_format = json_schema(strict)`（`llm.Client` 负责翻译成协议字段）。`strict` 是必要的——只有它真正约束**字段名**；`json_object` 只保证"是 JSON"，字段名照样由模型自起。
2. **降级**：schema 是**尽力而为**，不是保证。路由由 AMKR 侧决定、可以随时切（R9），而忽略 `response_format` 的行为**不一定报错**——静默返回散文比返回 400 更难发现。因此解析器必须同时接受 JSON 与文本前缀，且任何一步识别不出都退化成**一条 `thought`**，绝不丢内容。

字段名与提示词两处都写，是刻意的冗余：schema 被忽略时，prompt 里的字段说明是唯一还在起作用的约束。

> 为什么不让解析器只认 JSON：那会把"路由不支持"变成一个**静默的人格退化**（打算永远为空），而错误发生在 AMKR 侧、Sirius 看不到。文本兜底让最坏情况只是"类型不准"，不是"内容丢失"。
>
> 同理，解析上游回复时字段名有多套别名（`intent`/`next`/`打算` …）：忽略 schema 的路由会让模型自起字段名，别名表把这些仍归到正确类型。

### 8.6 消息入队不写正文

消息进 unread 队列时，意识流里只留一条**不含正文**的提示（"有人叫我" / "有新消息，但没叫我"）。

正文只能在"看 QQ"状态由 `ReadPhone` 读出（§2.2 + R7 修订的门控）。若入队时顺手把正文记进意识流，**QQ 门控就被旁路了**——不论在哪个状态，消息内容都会出现在 prompt 里。

## 9. 实施分期

### Phase 1（MVP）

- unread 队列 + 三类消息标记（`@`/回复只是"更显眼"，**不打断**）+ 已读游标
- "看 QQ"状态：进入返回最近 N 条 + 翻阅工具（分页）
- **待选区写入**：看手机时看到的内容自动入库（`Scan`/`Browse` 的副作用），关键词由本地词元化产出
- 打捞：查询侧同样切词元，按重合度 + 稀有度加权匹配，返回整段
- 记忆曲线衰减 + Shadow（含审计接口）
- 升格：达到 §5.3 条件 → 事件记忆，源条目删除
- **带类型的意识流 + 上下文装配**（§8）：独白由 LLM 生成、意图跨状态存活

**不做**（只是顺序靠后，不是放弃）：向量检索（Phase 1 用关键词 + LLM 重排）、LLM 整合、自我模型。

> 这条链路曾经整条是空的：四层记忆都有实现、都有单测，但**没有任何写入方**，于是 staging 恒为 0、打捞恒空、升格与 Shadow 永不发生。更隐蔽的是打捞本身——调用方传整句、匹配端做子串，两侧各自都"对"，合起来永远不命中，而 `Dredge` 有生产调用方，代码路径看着完全正常。
> 两条测试专门守它：`TestDredgeMatchesNaturalLanguageQuery`（整句查询必须命中）与 `TestAcceptanceMemoryWriteChain`（走真实 HTTP 入口的端到端）。快照里的 `memory.staging` 字段用于在**生产环境**直接看出它是不是 0。

### Phase 2

- **向量库**（§5.2）：Go 内暴力余弦 + 两路融合排序、embedding 模型标识与重建
- LLM 整合（event → consolidated，源进 Shadow）
- 自我模型 + 通道 B 常驻 prompt
- 通道 A：整合记忆参与检索打分
- 查询扩展：让独白产出关键词/近义表达（见 §5.1 的已知弱点）

### Phase 3

- 规模优化：若记忆条目增长到暴力余弦成为瓶颈，再考虑 ANN 索引
- 多 agent 互动

### Phase 1 验收

跑 30 tick 后能观察到：

1. 不在看 QQ 时消息**不进 prompt**
2. `@` **不打断状态**，但未读计数与烦躁确实随之增长；`sleeping` 不订阅 QQ，因此内容对它不可见
3. 退出再进入"看 QQ"时，已读游标使内容**向前推进**，不空转
4. 有记忆因长期不打捞而**沉入 Shadow**，且 Shadow 内容**不出现在 prompt**
5. 意识流由 LLM 生成（`call_count > 0`），且记录带类型
6. "打算做什么"在换状态后**仍然存在**
7. 上下文按调用点装配，各段**不超上限**
8. 状态确实会转移，且每次决定都能在 R6 日志里查到理由与当时的候选清单
9. **看手机后待选区非空**（`memory.staging > 0`），且用**整句**意图能打捞回刚看到的内容，反复打捞会升格出事件记忆

> 验收 5–7 对应 `internal/acceptance` 里的端到端测试。它们存在的理由很直接：
> `Think` 与 `Ingest` 都曾经没有任何生产调用方，而所有单测照样通过——
> 装起来的系统只是一个跑得挺欢的状态机加四条硬编码旁白。**凡是要跨越
> 模块边界才能成立的行为，都必须有一条走真实入口的验收测试。**
