# 记忆与注意力模型

本文档定义 Sirius 的**记忆分层、注意力门控、遗忘**机制。这是人格可信度的主要来源，也是与 AGENTS.md R5 配套的实施细则。

设计由项目作者提出，本文档是整理、评估与实现约束。

---

## 1. 设计目标

模拟一个**有注意力的存在**，而不是一个随时待命的问答接口。

核心命题：**信息可见性不是全开的。** 没在"看 QQ"的时候，群里的消息不该进入模型的视野——就像真人不会盯着屏幕等消息。

---

## 2. 注意力门控：消息如何进入

### 2.1 静默接收 vs 即时打断

| 消息类型 | 行为 | 现实对应 |
|---|---|---|
| `@我` | **即时打断**：立刻让 agent 切到"看 QQ"状态 | 手机弹通知 |
| **回复我**（引用/回复某条我的消息） | **即时打断**，同上 | 手机弹通知 |
| 其他消息 | **静默接收**：只入队，不进入 prompt | 群消息静默，只是红点数字 |

⚠️ **打断必须过 guard，不能无条件抢占。** 真人在睡觉/开会时不会被每条 @ 叫醒。建议：`@我` 与"回复我"是**高优先级事件**（对应 R3 的事件抢占），但目标状态若声明 `uninterruptible: true`（如 `sleeping`），则**延迟**到该状态自然退出，而不是丢弃。这个延迟量应该写进意识流（"睡着时被 @ 了三次"），它是人格的一部分。

### 2.2 未读队列必须有界

静默接收的消息进一个 **unread 队列**。因为 agent 可能长时间不进"看 QQ"状态，这个队列会无界增长（违反 R5）。约定：

- 队列设上限，超出时**按重要性丢弃**，不是简单丢弃最旧的
- 保留**未读计数**（它是心境的输入：99+ 会让"烦躁"上升）
- 队列内容本身只在进入"看 QQ"状态时被读取

### 2.3 读取有两级

1. **进入状态时**：显式返回**最近几条**消息（模拟"解锁手机扫一眼"）
2. **翻阅工具**：主动向前翻页，看更早的内容

**必须有已读游标（read cursor）。** 否则"最近几条"会永远返回同样几条，状态退出再进入时空转。

## 3. 记忆的四层结构

```
消息（原始）
   │ 静默入队 / 打断
   ▼
unread 队列 ──进入"看QQ"状态──► 最近N条直接进 working
   │
   │ 翻阅（翻阅工具，分页）
   ▼
┌─────────────────────────────────────────────┐
│ 1. 记忆待选区（staging）                      │
│    · 翻到的内容整批进入                        │
│    · 只用【关键词打捞】                        │
│    · 打捞返回「某次翻阅的全部上下文」（整段）    │
│    · 带记忆曲线：长期不打捞 → Shadow（遗忘）    │
└─────────────────────────────────────────────┘
   │ 被高频反复打捞 → 升格
   ▼
┌─────────────────────────────────────────────┐
│ 2. 事件记忆（event）                          │
│    · RAG + 关键词赋分 打捞                     │
│    · 长期低频 → LLM 整合（细节丢失，等同遗忘）  │
└─────────────────────────────────────────────┘
   │ LLM 整合
   ▼
┌─────────────────────────────────────────────┐
│ 3. 整合记忆（consolidated）                   │
│    · 抽象摘要，只能记得"大意"                   │
└─────────────────────────────────────────────┘

另：4. working memory —— 当前状态的即时上下文，进 prompt 的就是它
```

与 Generative Agents 的对应关系：待选区 ≈ observation，整合记忆 ≈ reflection。**但你的设计多了一个关键机制：主动翻阅 + 打捞，而不是被动被动接收观察。** 这是有意的区别（见 §6）。

---

## 4. 遗忘：这是设计的核心，不是副作用

三层遗忘机制，成本与粒度递增：

| 机制 | 触发 | 结果 | 实现成本 |
|---|---|---|---|
| **记忆曲线衰减** | 长期未被打捞 | 沉入 Shadow，仍存在但不再主动浮现 | 零（只改权重） |
| **LLM 整合** | 长期低频的事件记忆 | 丢弃细节，只留摘要 | 一次 LLM 调用 |
| **重要性淘汰** | unread 队列满 | 直接丢弃 | 零 |

⚠️ **Shadow 的实现定义待确认**（见 §7）：我暂按"低优先池"理解——记录仍在存储里（可被显式查询/审计），但不参与常规打捞排序，也不再刷新记忆曲线。如果你的意思更接近"物理删除"，实现差别很大。

---

## 5. 打捞（检索）的两个层次

### 5.1 待选区：关键词打捞

- 存储时**由 LLM 生成关键词**并落库，不要只存原文
- 打捞用关键词匹配，**返回整段翻阅上下文**（episodic，一整次翻阅的所有内容）

⚠️ **为什么返回整段而不是单条：** 单条消息脱离上下文会失去含义（"那你去吧"指什么？）。按"一次翻阅"作为检索单位，等价于人类的情节记忆——想起的是"那天翻聊天记录看到的那一段"，不是孤立的一句话。

⚠️ **关键词检索的已知弱点：** 同义词、代词、隐含指代都匹配不上（中文尤其）。Generative Agents 用 embedding 正是为了绕开这个。**最低成本的补偿：让 LLM 做查询扩展**——agent 想打捞时，先让它产出若干个关键词/近义表达，再逐个匹配。这比引 embedding 便宜得多，且不依赖外部服务。

### 5.2 事件记忆：RAG + 关键词赋分

- 向量召回 + 关键词打分融合排序
- 这是唯一需要 embedding 的地方

⚠️ **阻塞项：AMKR 目前没有 embeddings 端点。** 已核对 `auto_model_key_router` 全部源码，`embeddings` **零匹配**——没有专门的 embeddings 处理逻辑。

不过**泛型透传是通的**：`/v1/{path:path}` 会兜住 `POST /v1/embeddings`，`_upstream_path()` 对未知 mode 返回 `v1/{path}` 原样转发，`_resolve_model_id()` 从 `payload["model"]` 取模型名。

**所以三条路：**

| 方案 | 前提 | 代价 |
|---|---|---|
| A. 走 AMKR 透传 | 在 AMKR 里把 embedding 模型配成一个"模型"并绑 Key；上游支持 `/v1/embeddings` | 零 Sirius 改动，但依赖 AMKR 侧配置 |
| B. Sirius 本地 embedding | Go 里跑小模型 | 引入 cgo/模型文件，违反"标准库优先"，v1 不建议 |
| C. 先不做 RAG | 事件记忆也用"关键词 + LLM 重排" | 零依赖，效果打折但可用 |

⚠️ **我的建议是 C 起步、A 作为升级路径。** 理由：你的待选区已经是关键词打捞，事件记忆用同样的机制，**可以先跑起来验证"遗忘与打捞"这套机制本身是否产生可信行为**，再决定要不要为向量检索付出配置成本。这符合 MVP 收敛原则。

⚠️ 需要注意 A 方案的一个细节：embedding 请求要能在 AMKR 里被路由，就得有个"模型"条目。如果直接借用已有 chat 模型的名字，`_upstream_body` 会把 model 字段改写成上游模型名，可能对不上。**这需要 AMKR 侧配合验证**（那边的会话负责）。

## 6. 这套设计的优点（以及为什么它比论文更适合你）

1. **注意力门控解决了"信息全开"的不真实感。** 论文的 agent 感知是环境推送的（走到哪看到哪），没有"我不想看"这个维度。你的设计里 agent **主动决定何时看**，这本身就是人格。

2. **"返回整段翻阅上下文"是正确的检索单位。** 情节记忆优于碎片检索，且天然限定了 prompt 体积。

3. **遗忘是显式的三层设计**，而不是"上下文爆了就裁掉"。论文只有 recency 衰减这一种，没有 LLM 整合这一层。

4. **待选区用关键词而非向量，是有意的降级，且合理。** 联想记忆（cued recall）本来就是线索驱动的；关键词打捞在语义上比你想象的更接近人类回忆——"我是被什么提醒才想起这件事的"。

5. **@ 与回复的门控精确对应了现实的通知机制。** 这不是随意选的两类，而是"手机真的会响"的那两类。

## 7. 需要你确认或补充的四个点

| # | 问题 | 为什么重要 |
|---|---|---|
| 1 | **Shadow 的确切语义**：低优先池（仍存可查）还是物理删除？ | 决定存储设计；也决定能否审计"agent 忘了什么" |
| 2 | **"高频多次打捞"的升格阈值** | 需要一个具体数字才能实现；建议同时引入 importance 打分做对冲（见下） |
| 3 | **升格后待选区条目是否保留** | 保留=可回溯原文；删除=更"像遗忘"但丢失证据 |
| 4 | **整合记忆能否被检索并影响行为** | 论文证据表明反思**必须能参与检索**才有价值；若只当墓碑，就浪费了这层 |

### 7.1 关于升格阈值的一个警告

你现在的升格信号只有**频率**。这会产生**富者愈富**的反馈：被打捞→刷新记忆曲线→更容易再被打捞。论文的 recency 有同样性质，但它用 **importance（写入时 LLM 打 1–10 分）** 做对冲。

**建议：写入待选区时，顺手让 LLM 打一个 importance 分**（和生成关键词合并进同一次调用，几乎零额外成本）。升格条件从"被打捞 N 次"改成"被打捞 N 次 **或** importance ≥ 阈值且被打捞 ≥ 1 次"。这样"被 @ 的那条重要消息"不会因为没人翻到而消失。

## 8. 与 AGENTS.md 硬规则的关系

| 规则 | 本设计的对应 |
|---|---|
| **R5**（意识流有界） | 四层各自的边界见 §3；unread 队列上限见 §2.2 |
| **R3**（事件抢占） | `@我` / 回复我 = 高优先级事件；但受 `uninterruptible` guard 约束（§2.1） |
| **R2**（心境正交） | 未读计数 → 烦躁；反复打捞某段记忆 → 好奇/执念。心境**不**参与记忆存储 |
| **R8**（只认 tick） | 记忆曲线按 **tick** 衰减，不按 wall clock。否则回放会失真 |

### 8.1 关于 R7 的一个重要澄清

AGENTS.md R7 写的是"工具白名单"，而调研（`prior-art.md` §3.3）的教训是"**不要把工具可见性绑在状态上**"。

**你的 QQ 设计恰好是这个例外的正当理由**：门控的不是工具本身，而是**信息**。不在"看 QQ"状态时，`read_app` 之类的工具**仍然可用**，但没有 QQ 消息可读——因为消息不在 unread 之外的地方显现。

⚠️ **建议据此修订 R7 的措辞**：状态声明的是**信息可见性**与**建议动作**，不是工具白名单；只在有安全理由时才硬封锁具体工具。这个修订需要你确认，因为它改变了一条已定稿的硬规则。

---

## 9. MVP 取舍

第一版**只做**：

- unread 队列 + `@我`/回复 的即时打断（带 `uninterruptible` guard）
- "看 QQ"状态：进入返回最近 N 条 + 一个 `read_app` 翻阅工具（分页）
- 待选区：LLM 生成关键词 + importance 分，关键词打捞返回整段
- 记忆曲线衰减 + Shadow（低优先池）
- **不做** RAG/embedding（事件记忆先用关键词 + LLM 重排）
- **不做** LLM 整合（先把"遗忘"跑通，整合放第二步）

验收：跑 30 tick 后，能观察到——① 不在看 QQ 时消息不进 prompt；② 被 @ 时能打断；③ 睡觉状态下 @ 不打断但有记录；④ 有记忆因长期不打捞而沉入 Shadow。
